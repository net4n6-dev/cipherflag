# CipherFlag CE Roadmap and Deferrals

Per-item ledger of open work in CipherFlag CE. Items are tagged by what they are, not by the release they "must" land in, and when one ships it is marked with a lead ✅, the date and the resolving commit rather than deleted. Ids are `ce:NNNN`. README's "Status and roadmap" table stays the capability-level view; this file is the defect-level view.

**Tag legend:**
- `[correctness]` current behaviour is wrong, fragile, or surfaces a real failure mode operators will hit
- `[hardening]` improves robustness, observability, or operator experience without fixing a strict bug
- `[capability]` net-new functionality
- `[docs]` the product is right and a document about it is wrong, missing, or hand-transcribed from code that has since moved
- `[maintenance]` dead weight to remove

**Reading an entry.** A filing's Symptom (with `file:line`) is evidence; its Fix is a hypothesis written by whoever filed it. Re-scope from the code before building. The `(origin: ...)` note says where the item came from; review-origin filings have historically been right about the symptom and wrong about the fix.

## Follow-ons from the 2.3.1 bug hunt (2026-09-28)

Found by a three-reviewer pass over `fix/2.3.1-zeek-ingest` (the five commits on v2.3.0 that restore Zeek ingest): the code-review skill over the diff, a poller/sensor review with throwaway reproduction tests, and an operator-path review of config, Settings, compose and docs against the code. Every item below was re-verified in the code before filing. Line numbers are as of commit `13042a0`. None were fixed on the branch; the poller items marked `[correctness]` are the ones most worth fixing before 2.3.1 ships since they live in the pipeline the release restores.

### Scoring

- ✅ 2026-09-28 (43fdbed) `[correctness]` **A stock install never scores anything: `scorer_enabled` defaults to false, the shipped config does not set it, and no document mentions it.** Symptom: `internal/config/config.go:68` declares `ScorerEnabled` with a zero default (comment at `:804`); `config/cipherflag.toml` never sets it; `cmd/cipherflag/main.go:161` starts with `scoring.NewNoopScorer()` and only builds the real dispatcher and the recheck sweeper inside `if cfg.Analysis.ScorerEnabled` (`:174-191`). ### Zeek log poller (`internal/ingest/zeekfile`)

- ✅ 2026-09-28 (adf70db) `[correctness]` **Observations are not idempotent, so every poller re-read duplicates TLS sessions.** Symptom: `RecordObservation` in `internal/store/postgres.go:820-832` is a plain `INSERT` with no unique key and no `ON CONFLICT` (the `observations` table in `internal/store/migrations/v2.0_baseline.sql:124-144` has only non-unique indexes); the poller calls it per line at `poller.go:383`, bypassing the ingester's observation cache. Certificates are upserted and are idempotent; observations are not. Three reproduced triggers: **(a)** a cursor entry is dropped the first poll its file is absent from the listing (`poller.go:151-159`) and the file is re-read from offset 0 when it reappears. Zeek 9.0.0's `Log::rotation_format_func` first renames `x509.log` to `x509-YY-MM-DD_HH.MM.SS.log` (hyphen) and only then the ASCII postprocessor moves it to `x509.YYYY-MM-DD-HH-MM-SS.log`; the intermediate name matches neither `x509.*.log` nor `x509.log`, so a poll during that window drops the entry (reproduced: 4 sessions became 8 observations). The Glob-then-Stat gap at `poller.go:213-223` and `listFiles` returning nil when `log_dir` is momentarily unreadable (`poller.go:187-194`, which wipes the whole cursor) do the same. **(b)** `RecordObservation` fails on the Nth observation of a batch (`poller.go:366-389`): the cursor is correctly not advanced but the first N-1 inserts are committed, and the retry inserts them again (reproduced: failure on 3 of 4 gave 6 observations). **(c)** `process` succeeds and `saveCursor` fails (`poller.go:265-271`): the whole batch is re-ingested next poll. The same duplication follows every cursor reset the code allows (unreadable or legacy cursor, the inode-reuse heuristic, the non-unix path-keyed rotation). `docs/architecture.md:89-93` ("read again, which is harmless because ingest is idempotent"), `docs/cipherflag-user-guide.md:279-280` and the comment at `poller.go:415` all claim idempotence; it holds only for certificates. Fix: add a unique index on `(cert_fingerprint, source, observed_at, client_ip, server_ip, server_port)` with `ON CONFLICT DO NOTHING`, or write a batch's observations and its cursor in one transaction; and keep cursor entries for absent files for a grace period (N polls, or until the stored `Path` is also gone) instead of dropping on the first miss. Delivered as the unique index plus `ON CONFLICT DO NOTHING`; the grace period for cursor entries of absent files was not done (a dropped entry now only costs a re-read). (origin: 2026-09-28 bug hunt, poller review and code-review skill) <!-- ce:0002 -->

- `[correctness]` **ssl sessions are silently lost when the x509 backlog exceeds the 16 MB per-file cap in the same poll.** Symptom: "x509 before ssl" (`poller.go:84`) holds only within one poll, but each file is read through `io.LimitReader(fh, maxReadPerFile)` (`poller.go:257`) with no signal back to `PollOnce` (`:163-166`) that the cap was hit. So an `x509.log` backlog past the cap is not fully read before `ssl.log` is read; ssl lines that reference certs not yet ingested count as `observations_unknown_cert` (`:375-381`) and the ssl cursor advances past them for good. Reproduced: x509.log of 16 MB plus a few lines whose last cert is referenced by ssl.log; poll 1 ingests 4098 certs and records 0 observations with 1 unknown; poll 2 ingests the remaining certs and still records 0. This is exactly the upgrade-from-2.3.0 backlog case the changelog describes ("worked through 16 MB per file per poll"). A narrower steady-state variant exists: Zeek's x509 and ssl writers are separate threads flushed on about 1 s heartbeats, so an ssl line can hit disk before its x509 line and a poll in that window loses the session the same way. Fix: have `readFile` report "hit limit" and skip ssl files in any poll where an x509 file did, and/or do not advance the ssl cursor past a batch containing unknown-cert sessions (hold them for a few polls before dropping). (origin: 2026-09-28 bug hunt, poller review) <!-- ce:0003 -->

- `[correctness]` **A fingerprint/PEM mismatch is skipped silently inside ingest but the poller still marks it known, and the resulting foreign-key violation blocks every later file forever.** Symptom: `UnifiedIngester.Ingest` handles `dedup.ErrPEMMismatch` with a warning and `continue` and returns no error (`internal/ingest/ingester.go:181-185`); `processX509` then sets `known[fp] = true` for every discovery it sent (`poller.go:330`). The ssl line for that chain calls `RecordObservation`, which fails on `observations.cert_fingerprint REFERENCES certificates` (`v2.0_baseline.sql:126`). `PollOnce` returns on the first `readFile` error (`poller.go:163-166`), before later files and the final `saveCursor`, so the ssl cursor never advances, the same batch is retried every 30 s (re-inserting the rows that preceded the failure, see ce:0002), and every file after it in the listing (later ssl files, all `.done` job directories) is never read. The same availability failure follows a single rotated file that cannot be opened (permissions). Fix: use the `IngestionSummary` (or re-check the store) instead of assuming every discovery was stored, and have `PollOnce` log and continue to the next file, returning the first error after the loop. (origin: 2026-09-28 bug hunt, code-review skill and poller review) <!-- ce:0004 -->

- `[correctness]` **A certificate Go cannot parse is stored as a blank row instead of falling back to x509.log's fields.** Symptom: `certDiscovery` (`poller.go:344`) sends only `FingerprintSHA256` and `RawPEM` when the sensor logged the DER, deliberately dropping `SubjectCN`, `NotAfter`, `KeyAlgorithm` and the rest; `dedup.candidateFromDiscovery` (`internal/ingest/dedup/deduplicator.go:204-209`) swallows the parse error and builds from `&model.Certificate{}` plus the (now empty) discovery fields. Scenario: Zeek (OpenSSL) logs a certificate Go's `x509.ParseCertificate` rejects (negative serial, malformed SAN or UTF-8, duplicate extension): the row has an empty CN, zero `not_after`, empty algorithms and an unparseable `raw_pem`, `incompleteCert` stays true so every re-sighting re-parses forever. Fix: parse the PEM in `certDiscovery` (as `ct.BuildCertDiscovery` does) and fall back to `zeek.MapX509ToCertificate` fields on failure. (origin: 2026-09-28 bug hunt, code-review skill) <!-- ce:0005 -->

- `[hardening]` **A line longer than 16 MB stalls its file forever.** Symptom: a line that does not end within `maxReadPerFile` is treated as "incomplete, retry next poll" (`poller.go:257`, `:273-282`), but it can never complete, so the offset stays put, 16 MB is re-read every poll (about 6 ms on APFS, so I/O not CPU) and every line after it in that file is never ingested; other files are unaffected. Reproduced: 3 polls, 0 certificates, offset 0 each time. Unlikely from real Zeek output (TLS caps a certificate message at 16 MB) but permanent and silent. Fix: if the read hit the limit without consuming any complete line, scan forward to the next newline, advance the cursor past it and count it as unparseable. (origin: 2026-09-28 bug hunt, poller review) <!-- ce:0006 -->

- `[hardening]` **Inode reuse is detected only when the new file is smaller than the stale offset.** Symptom: `poller.go:239-243` resets the cursor on size regression only. A rotated log deleted between two polls (as the docs instruct) and a new file created with the same dev:inode that is already at least as large keeps the old offset: the first read starts mid-line (one unparseable line) and the bytes before the offset are never ingested. Not reproducible on APFS (inodes are not reused); plausible on ext4 and overlay2 where freed inodes are reused quickly. Fix: the cursor already stores `Path`; a rotated name never changes again, so if the stored `Path` is a rotated name and the current path differs, restart from 0; additionally check that the byte before the offset is a newline before resuming. The non-unix path-keyed fallback (`fileid_other.go`) has the mirror problem (rotated file is a new id and re-read in full; new live file resumes at the old offset) but is not a supported deployment. (origin: 2026-09-28 bug hunt, poller review and code-review skill) <!-- ce:0007 -->

- `[hardening]` **One `INSERT` round trip per observation inside the per-line loop.** Symptom: `poller.go:383` calls `RecordObservation` per line, plus a `GetCertificate` per new fingerprint, for batches of up to 500 lines each yielding a chain of 2-4 observations, while the x509 side is batched through `Ingest`. A busy sensor at about 1000 TLS 1.2 sessions a minute means 2000-4000 sequential `Exec` calls per poll on the shared pool. `store.BatchRecordObservations` still exists on the `CryptoStore` interface (`postgres.go:865`). Fix: one transaction per batch with `pgx.Batch` or `CopyFrom`, which also gives the atomicity ce:0002 needs. (origin: 2026-09-28 bug hunt, code-review skill) <!-- ce:0008 -->

### Zeek sensor image (`docker/zeek`)

- `[correctness]` **A job directory holding more than one capture processes only the first and ignores the rest forever.** Symptom: `docker/zeek/entrypoint.sh:11` iterates per PCAP file (`*/*.pcap` and `*/*.pcapng`, so multiple files per directory are explicitly allowed) but the `.done` and `.failed` markers are per job directory (`:16-17`). Scenario: `a.pcap` and `b.pcap` in `pcap-input/job-1/`; `a.pcap` runs, `.done` is written, `b.pcap` hits the `continue` on every pass and is never processed or reported; if `a.pcap` fails, `.failed` blocks `b.pcap` too. Fix: key the markers per file, or reject and log multi-file job directories at the sensor and document one capture per job. (origin: 2026-09-28 bug hunt, code-review skill) <!-- ce:0009 -->

- `[correctness]` **The user guide's cleanup instruction makes the sensor reprocess the job and the poller ingest it twice.** Symptom: `docs/cipherflag-user-guide.md:677` says to remove rotated logs and finished job directories from the zeek-logs volume once CipherFlag has read them; the PCAP watcher (`entrypoint.sh:11-17`) reprocesses any `<pcap-input>/<job>/*.pcap` whose `<logs>/<job>/.done` and `.failed` are absent, so deleting the finished job directory removes the marker and Zeek re-runs the capture within 5 s, writing new log files (new inodes) that the poller reads as new: every certificate is re-upserted (fine) and every TLS session of the job is recorded again (ce:0002). Contradicts user guide 279-280 ("A job is processed once"). Fix: keep the processed marker somewhere the cleanup does not touch (for example `.done` beside the pcap in pcap-input), or tell operators to delete only `*.log` inside the job directory and keep `.done`; correct the doc either way. (origin: 2026-09-28 bug hunt, poller review) <!-- ce:0010 -->

- `[hardening]` **A PCAP still being copied is processed truncated and never retried.** Symptom: the watcher picks a file up the moment it appears (checked every 5 s, `entrypoint.sh:11-32`); a partially copied file is run through Zeek truncated and permanently marked `.done` (partial results) or `.failed`, and the completed upload is never processed because the marker exists. The docs tell users to `cp capture.pcap pcap-input/<job>/`, a non-atomic copy. Fix: require the size to be unchanged across two scans (or an mtime older than about 10 s) before running Zeek, or document copying to a temporary name and `mv` into place. (origin: 2026-09-28 bug hunt, poller review) <!-- ce:0011 -->

- `[hardening]` **The sensor never deletes rotated logs or finished job directories, so the zeek-logs volume grows without bound.** Symptom: nothing in `docker/zeek/` or the compose file prunes `x509.*.log`, `ssl.*.log` or `<logs>/<job>/`; the only cleanup is the manual instruction at user guide 677, which is itself wrong (ce:0010). Fix: a retention setting in the sensor (delete rotated logs older than N hours and job directories whose `.done` is older than N hours) once the poller's cursor design makes deletion safe (ce:0007), and a doc sentence stating the retention. (origin: 2026-09-28 pre-hunt known finding, confirmed) <!-- ce:0012 -->
